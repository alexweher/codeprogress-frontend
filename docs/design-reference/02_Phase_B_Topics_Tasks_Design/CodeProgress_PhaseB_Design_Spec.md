# CodeProgress 2.0 — Premium UX / Phase B

**Статус:** завершённый дизайн-концепт и техническая постановка, **не внедрён в React**.
**Дата:** 14 ноября 2026
**Область:** Topics list, Topic details, LearningTask details и формы; StudySessions — согласованный визуальный ориентир для Phase C.
**Основа:** текущий Phase A, CodeProgress Design Blueprint v2, проверенные frontend/API reports, пользовательские скриншоты от 14 ноября 2026.

## 1. Product brief

### Ключевая проблема

В текущем продукте есть реальные API и данные, но пользователю приходится разбираться в разных технических сущностях (`Topic`, `LearningTask`, `StudySession`), статусах и последовательности действий. Мотивацию нельзя решить одним градиентом и крупными карточками: человеку нужен **один очевидный следующий шаг** и честное представление о прогрессе.

### Продуктовая концепция

CodeProgress — **личный маршрут обучения программированию**. Человек сам создаёт учебные направления, определяет конкретные задачи, практикуется и фиксирует результаты. Это не автоматический курс и не AI-репетитор; никакой выдуманной персонализации.

**Главный цикл:** Мои темы → выбрать тему → выбрать/создать задачу → работать над ней → записать занятие → увидеть фактический прогресс → выбрать следующий шаг.

### Принципы

1. **Action before decoration:** полезное действие выше декоративных элементов.
2. **Honest progress:** 1/1 выполненная задача — завершены поставленные задачи, а не «знание Java на 100%».
3. **Self-directed path:** учебные шаги — реальные `LearningTask`, порядок не выдавать за педагогически оптимальную последовательность.
4. **Context preservation:** занятия привязаны к Topic, а не к отдельной Task; не придумывать дополнительные API.
5. **Clear hierarchy:** одно primary-действие на экран, вторичные вынести в меню/боковую панель.
6. **Bilingual first:** весь статический UI ru/en; введённые пользователем названия/заметки никогда автоматически не переводить.
7. **Safe by design:** JWT в памяти, user-scoped query cache, подтверждение удаления, данные пользователя не трогать при редизайне.

## 2. Информационная архитектура

```text
CodeProgress
├── Мой прогресс         (/app/dashboard)          [Phase A — сохранить]
├── Мои темы             (/app/topics)             [Phase B — редизайн]
│   └── Java Collections (/app/topics/:topicId)    [Phase B — редизайн]
│       ├── Учебные задачи (в контексте темы)       [Phase B]
│       │   └── Изучить ArrayList → существующий /app/tasks/:taskId или фактический маршрут из router.tsx
│       └── Учебные занятия (в контексте темы)      [Phase C — позже]
└── Настройки            (/app/settings)           [Phase A — сохранить]
```

**Важно:** указанный путь Task — описательный; Codex должен использовать точные реальные пути из текущего `src/app/router.tsx`, не изобретать новый роутинг. Отдельные глобальные Tasks/Sessions не добавлять без поддерживаемых API и отдельного решения.

## 3. Экраны и UX

### Экран B1 — «Мои темы»

**Первый экран содержит:**

- небольшой eyebrow «Твои направления»;
- понятный H1 «Чему учимся сегодня?»;
- одно основное действие «Новая тема»;
- список реальных Topic cards, без фальшивых курсов;
- в каждой карточке название, описание, **отдельный статус темы**, task-completion `done / total`, полоса выполнения задач и реальное время занятий (только если достоверно агрегируется из sessions конкретной Topic);
- переход на Topic detail через доступную ссылку.

**При одном направлении:** одна выразительная карточка + dashed «Добавить направление» (не навязчиво); никакой имитации заполненного каталога.
**При нуле направлений:** один onboarding-блок «Создать первую тему»; убрать пустую статистику и графики.
**При множестве:** grid карточек, можно добавить сортировку только по настоящим доступным данным; не выдумывать прогресс от псевдокурсов.

### Экран B2 — страница темы

**Порядок контента:**

1. Breadcrumb «Мои темы / Java Collections».
2. Compact topic heading: название, описание, статус темы, «1 / 1 задач · 100% выполнения поставленных задач».
3. Main column — **«Твой учебный маршрут»**, список всех реальных задач, доступные состояния `PLANNED`, `IN_PROGRESS`, `COMPLETED`.
4. Ясное следующее действие: если активная задача существует, «Продолжить задачу»; если только запланированные — «Открыть следующую задачу»; если все закончены — «Добавить следующую задачу»; если задач нет — «Добавить первую задачу».
5. Secondary panel — статистика только этой темы, если данные доступны (task counts; study minutes и sessions по Topic).
6. Secondary panel — отдельный редактор статуса Topic и функции редактирования. Не связывать автоматически с Task status.
7. StudySession preview внутри темы и существующее действие «Записать занятие»; полноценный редизайн формы/истории — Phase C.

**Тонкое правило:** статусы Topic (`PLANNED | IN_PROGRESS | COMPLETED`) — решение пользователя. `COMPLETED` отдельной задачи не должен самостоятельно превращать Topic в `COMPLETED` без явно существующей backend-логики. Пояснить это в интерфейсе, особенно при 100% task-completion.

**Учебный маршрут** — это структура вокруг _реальных_ задач. Нет «замков», «бесплатных уроков» или фальшивых уровней. Приоритет/сложность/дедлайн выводятся только если есть в ответе DTO.

### Экран B3 — страница учебной задачи

1. Breadcrumb назад к Topic.
2. Заголовок — введённый пользователем `title`, без автоматического перевода.
3. Статус текстом, контекст Topic, difficulty, priority, deadline (nullable), описание.
4. Одна главная CTA в зависимости от статуса:
   - PLANNED → «Начать задачу» (`PATCH status IN_PROGRESS` если это уже поддержано);
   - IN_PROGRESS → «Завершить задачу» (с пониманием, фиксируется ли занятие отдельно);
   - COMPLETED → «Добавить следующую задачу» (в текущей теме).
5. Вторичные функции — «Редактировать задачу», «Изменить статус», «Изменить планирование», «Удалить» с подтверждением.
6. Переход к занятиям — в контексте **Topic**, не «прикрепить занятие прямо к задаче».

Нельзя утверждать, что Task completion автоматически создаёт StudySession. `StudySession` со списком `completedTaskIds` — отдельная операция с атомарным backend-изменением задач; сохранить этот смысл и явное подтверждение в форме.

### Экран C1 — история занятий (только дизайнерский концепт Phase C)

Карточка занятия: фактическая календарная дата, длительность, `note`, _только реальные_ completedTaskIds, переход к существующей форме подробностей/редактирования. Отображение русских/английских дат через календарную семантику `LocalDate` без UTC-сдвига.

Сохранить в будущем создание StudySession с `sessionDate`, `durationMinutes` (positive), `note` (max 2000), `completedTaskIds` (nullable? **нет** — required set, может быть пустым). Не заставлять пользователя отмечать выполненную задачу при каждом занятии.

## 4. Правила дизайна / дизайн-система

Совместима с Phase A, не переписывает уже согласованные UI primitives.

| Сущность        | Токен / правило                                                         |
| --------------- | ----------------------------------------------------------------------- |
| Фон             | `#F5F7FC`, мягкие сиреневые/мятные локальные подсветки                  |
| Карточки        | `#FFFFFF`, радиусы 20–24px, тонкая граница `#E5EAF3`                    |
| Основной текст  | `#1D2641`                                                               |
| Вторичный текст | `#687793` (проверить фактические контрасты)                             |
| Primary action  | `#6447DD`, hover `#4E33BF`                                              |
| Completed       | текст + check icon + мягкий зелёный оттенок                             |
| Planned         | текст + тёплый песочный оттенок                                         |
| In progress     | текст + фиолетовый акцент                                               |
| Типографика     | system/Inter if installed, H1 desktop ~38–48, mobile ~30–34, body 14–16 |
| Layout          | sidebar 248px desktop; bottom nav mobile; max content ~1360px           |
| Target sizes    | основные действия ≥44×44 CSS px                                         |
| Animation       | 140–220ms, reduced-motion respect                                       |

**Контраст и доступность:** целевой WCAG 2.2 AA, текст 4.5:1 (large 3:1), границы interactive controls 3:1 при применимости, visible keyboard focus, DOM order, labelled controls, modal focus trap/restore в production, error/empty/loading states. Значения необходимо проверить на реальном React — это целевые правила, не результат полного WCAG-аудита прототипа.

## 5. Данные и API: проверенные ограничения

- Topic: `title`, `description?`, `status PLANNED/IN_PROGRESS/COMPLETED`, `createdAt`, `updatedAt`. GET/PUT/PATCH согласно текущему API.
- Task: `title`, `description?`, `status PLANNED/IN_PROGRESS/COMPLETED`, `difficulty EASY/MEDIUM/HARD`, `priority LOW/MEDIUM/HIGH`, `deadline LocalDate?`, `topicId`.
- StudySession: Topic-scoped; `sessionDate LocalDate`, `durationMinutes`, `note?`, `completedTaskIds` — факт сохраняется в рамках Topic.
- Проверенные списки: `GET /api/topics`, `GET /api/topics/{topicId}/tasks`, `GET /api/topics/{topicId}/sessions`; Task details и mutation routes уже есть в проекте.
- Общий Dashboard summary не даёт готовой статистики _по каждой Topic_, поэтому Topic-card метрики возможны после получения списков для соответствующих тем. Не показывать случайно dashboard totals как показатели отдельной темы.
- Возможный N+1 при множестве тем: не запрашивать десятки полных списков без контроля; для карточек в первую версию допустимо показывать только достоверно доступные данные, с lazy-fetch/ограничением запросов или «Открыть тему для деталей» при большом объёме.
- `Topic.status` не вычислять из `Task.status`.
- `Task status` и `StudySession.completedTaskIds` могут влиять на одни и те же задачи по разным UI actions; сохранить существующую атомарность backend и cache invalidation.
- Не изменять tenant/user scoping; все API и query keys remain user-scoped.

## 7. Критерии качества

- Desktop 1440×900, tablet 768×1024, mobile 390×844, compact 320×700; без horizontal overflow.
- Доступность клавиатуры, viewport и reduced-motion; все статусы — с текстом.
- Локализация ru/en на новых экранах и формах, данные пользователя не переводятся.
- Реальные числа и прогресс из owner-scoped ответов; даты `LocalDate` без timezone bug.
- Existing typecheck/lint/unit/production build и подходящие mocked Playwright regression проходят.
- Не трогать Backend, PostgreSQL, Docker, API contracts, release tags, пользовательские записи.
- No commit/push without explicit user approval.

**UX-цели для отдельной ручной оценки (ещё не измерены):** 4 из 5 участников правильно понимают связь Topic/Task/Session; 4 из 5 находят следующую задачу без подсказок за 20 секунд; сценарий «создать тему → задачу → занятие» выполняют без внешней помощи. Эти значения — гипотезы, не результаты исследования.

## 8. Разделение реализации

**Phase B / сейчас:** Topics list, Topic detail, Task detail, task forms + общие визуальные состояния.
**Phase C / после ручного просмотра:** Sessions list/details/forms и Login/Registration.
**Phase D / после отдельного решения по Backend:** optional streaks / XP / milestones (без фиктивных очков и принуждения к активности).
