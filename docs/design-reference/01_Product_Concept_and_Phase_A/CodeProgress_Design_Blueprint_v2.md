# CODEPROGRESS 2.0 — Product & Experience Design Blueprint

**Версия:** 1.0 · **Дата:** 14 ноября 2026
**Статус:** концепция и реализуемое дизайн-задание; НЕ production и НЕ утверждение о выполненных изменениях в репозитории.
**Продукт:** CodeProgress — персональный трекер обучения программированию.
**Текущий стек (из проекта):** React/TypeScript/Vite; Spring Boot/Java; PostgreSQL; API для Topics, LearningTasks, StudySessions, Dashboard; ru/en локализация.

---

## 1. Executive summary

**Не строим очередной dashboard. Строим место, в которое хочется вернуться, чтобы сделать следующий осмысленный шаг в обучении.**

Функциональное ядро продукта: **Тема → Задача → Практика/занятие → Рефлексия → Видимый прогресс → Следующая задача.**

**Целевой опыт:** через 5 секунд пользователь понимает, что изучает; через 10 секунд — что ему делать дальше; за 1–2 клика начинает осмысленную работу. Это продуктовые _гипотезы и целевые критерии_, а не подтверждённые индустриальные нормативы.

**Креативная концепция:** «Learning Studio / Путь разработчика». Дружелюбная геймифицированная графика, точная информационная архитектура, взрослый визуальный язык, без копирования Duolingo. Новая палитра: фиолетовая энергия, мятно-зелёный успех, холодный фон, мягкие синие информационные состояния. **Мотивация — без манипуляций**: не вводить наказания за пропуски, искусственный дефицит, фальшивые XP и награды.

**Не нарушать существующее:** реальные аккаунты, данные и историю; Backend, API contracts, JWT in-memory, ru/en; работающие CRUD flows; релизный tag v1.0.0.

## 3. Продуктовая модель

### User job-to-be-done

«Я изучаю Java/Backend. Когда у меня есть свободные 20–30 минут, я хочу за секунды увидеть, что изучать сегодня, открыть конкретную задачу, отметить практику, сохранить заметку и увидеть реальный прогресс, чтобы не терять контекст между занятиями».

### Главный цикл

1. **Выбрать направление** — `Topic`: Java Collections, Spring Security, SQL.
2. **Выбрать понятный шаг** — `LearningTask`: конкретный результат, а не абстрактное «изучать Java».
3. **Практиковаться** — открыть задачу, пометить IN_PROGRESS, при необходимости зафиксировать `StudySession` с длительностью и заметкой.
4. **Закрыть шаг** — DONE после реальной работы.
5. **Увидеть движение** — `2 из 5 задач`, последние занятия, следующий доступный шаг.

**Ключевая граница:** текущие сущности не являются автоматизированным курсом с уроками. Нельзя изображать фиксированную педагогическую последовательность, автоматическую рекомендацию или адаптивную оценку знаний, пока такой логики нет. «Учебный путь» в UI — визуальное представление реальных задач, с прозрачным порядком и честными статусами.

### Три состояния при входе

- **Новый аккаунт:** короткий текст «Начни с первой темы», CTA «Создать тему», после создания — «Добавить первую задачу», после неё — «Отметить занятие». Никаких пустых графиков как главный контент.
- **Активная задача:** сразу CTA «Продолжить задачу» с реальным названием; рядом текущий учебный путь и возможность записать занятие.
- **Все задачи завершены:** «Отлично, 1 из 1 завершена» и CTA «Добавить следующую задачу» / «Открыть темы». Ни общего «100% освоения Java», ни фальшивого XP.

## 4. Информационная архитектура

### Desktop sidebar

- **Главная** — `Dashboard`: конкретный следующий шаг, текущий путь, минимальные полезные сводки.
- **Мои темы** — доступные направления/`Topic` list; клик → Topic details.
- **Задачи** — единый обзор только если его можно построить на поддерживаемых API; иначе route/contextual Topic selection (не фиктивная страница).
- **Занятия** — аналогично, на существующих API без изменения Backend.
- **Настройки** — язык ru/en (существующая возможность), будущие доступные настройки.

### Mobile

Нижняя навигация для 5 постоянных разделов при наличии реальных маршрутов. Если часть страниц пока не реализована — вместо «Soon» перейти к существующему доступному сценарию либо сократить набор вкладок. Главный CTA остаётся в контенте. Ни один контрол не перекрыт bottom nav; `padding-bottom` с учётом safe area. Адаптивность проверять на 320/390/768/1024/1440px и при 200% browser zoom.

### Терминология

| RU               | EN                | Значение                                                |
| ---------------- | ----------------- | ------------------------------------------------------- |
| Главная          | Home              | Домашний экран, не технический Dashboard                |
| Мои темы         | My topics         | Учебные направления (`Topic`)                           |
| Задачи           | Tasks             | Конкретные цели (`LearningTask`)                        |
| Занятия          | Sessions          | Журнал практики (`StudySession`)                        |
| Следующий шаг    | Next step         | Текущая/следующая доступная задача                      |
| Учебный путь     | Learning path     | Визуальная последовательность задач, не AI-рекомендация |
| Записать занятие | Log study session | Запись реального времени и заметки                      |

**Важно:** имена `Topics`, `LearningTask`, `StudySession`, enums и API в Backend не переименовывать ради UX.

## 5. Desktop dashboard: порядок сверху вниз

Сетка: sidebar 248px, main max width 1180px, content padding 32–40px, column gap 18–24px.

1. **Topbar**: CodeProgress / Главная, кнопка RU/EN при желании, аккаунт. На реальной версии не показывать DEMO и не помещать email в hero.
2. **Compact hero**: высота ~200–220px, заголовок до двух строк; одна главная кнопка «Продолжить обучение» → реальная задача/темы. Оригинальный декоративный элемент `< />`, без чужих персонажей. Hero не должен прятать продуктивный CTA.
3. **«Следующий шаг»** (первый смысловой блок, `minmax(0, 1.56fr)`) — текущая задача, краткий статус, контекст темы, actionable link. Если нет активной задачи — следующая запланированная, если нет задач — CTA создать задачу.
4. **«Учебный путь»** (правая колонка) — 3–5 реальных задач с состояниями DONE/IN_PROGRESS/PLANNED. Не рисовать «заблокировано» без backend-правил. Не маркировать всё как уроки, если это пользовательские задачи.
5. **Три лаконичные метрики** — выполнено задач (x из y), минуты практики, число занятий. Если нет знаменателя, не показывать «100%».
6. **Практика последних 7 дней** — только реальные дневные минутные данные; если API не предоставляет разбивку для нужного периода, скрыть блок или показать корректный fallback.
7. **Быстрая запись занятия** — обычная существующая форма, предвыбранная тема лишь когда контекст однозначен. Без новой мутации при просмотре.

**Не показывать одновременно несколько одинаковых «Продолжить с темами».** Единственный первичный CTA на каждом состоянии экрана. Остальные — вторичные.

## 6. Визуальная система и tokens

### Цвета

| Token                | Hex       | Использование                      |
| -------------------- | --------- | ---------------------------------- |
| `color.bg`           | `#F6F8FD` | Мягкий фон                         |
| `color.surface`      | `#FFFFFF` | Карточки, формы                    |
| `color.ink`          | `#202848` | Основной текст                     |
| `color.muted`        | `#61708A` | Вторичный текст; ~5.0:1 на белом   |
| `color.primary`      | `#674BDD` | Primary button; белый текст ~5.8:1 |
| `color.primaryHover` | `#573CBD` | Hover/active                       |
| `color.primarySoft`  | `#EDE8FF` | Focused path, мягкий фон           |
| `color.success`      | `#155B3B` | Текст успешного статуса            |
| `color.successSoft`  | `#DBF7E7` | Background success                 |
| `color.infoSoft`     | `#EAF3FF` | Info background                    |
| `color.warningSoft`  | `#FFF5DB` | Planned/hints                      |
| `color.border`       | `#E5E9F3` | Линии, разделители                 |

**Контраст:** указанные соотношения рассчитаны для указанных пар цветов, остальные комбинации необходимо проверить автоматически и вручную. Никогда не передавать значение статуса только цветом.

### Типографика

- Основной стек: `Inter`, `Manrope`, `Segoe UI`, system-ui; если шрифты не доступны, использовать system без блокирующих сетевых запросов.
- Заголовок H1 30–40px desktop, 27–30px mobile. H2 22–26px. H3 17–20px. Base 15–16px; вторичный текст 13–14px. Не использовать `11px` для критического действия.
- Межстрочный интервал основного текста 1.5–1.6. Не более 2 уровней акцентного веса в пределах одной карточки.

### Layout и формы

- Spacing system: 4, 8, 12, 16, 24, 32, 40, 48.
- Card radius 20–24px; input radius 12–14px; primary button radius 12–14px.
- Комфортные активные области: **целимся в >=44×44 CSS px**, это наше практическое правило. WCAG 2.2 AA требует >=24×24px с оговорёнными исключениями.
- Большая CTA только для главного действия; вторичные действия — light/outline/text.
- Shadows мягкие (Y8–14, blur24–40, alpha 4–7%), без чрезмерных глянцевых эффектов.
- Motion: 140–220ms, transform/opacity, `prefers-reduced-motion`. Не анимировать большие layout shifts.

### Original visual identity

Не использовать сову Duolingo, его лого, иллюстрации, идентичную структуру streaks/gems/hearts. Оригинальный элемент бренда — `< />` в скруглённой плитке плюс пиктограмма пути. Изображения, если понадобятся, должны быть оригинальными или законно лицензированными.

## 7. Системные UI-состояния

Для каждого компонента: default, hover, focus-visible, active, disabled, loading, empty, error, success.

- Loading: резервировать размеры карточек скелетонами, исключать layout shift.
- Network error: понятно объяснить «Не удалось загрузить данные» + «Повторить», не очищать пользовательские формы.
- Empty topic: объяснение «В этой теме ещё нет задач» + CTA «Добавить задачу».
- No sessions: «Ты ещё не записывал занятия» + CTA «Записать первое занятие».
- Completed: положительная обратная связь, без выдуманной оценки знаний.
- Destructive delete: confirm со специфичным объектом, возможность отменить если поддержана; сохранить существующее поведение API.
- Auth expiry/reload: сохранить понятную экранную навигацию и locale, но не переносить JWT в persistent storage.

## 8. Доступность и производительность

### Подтверждённые внешние стандарты

**WCAG 2.2 AA**: контраст обычного текста не ниже **4.5:1**, крупного **3:1**, значимых не-текстовых UI элементов **3:1**; target minimum **24×24 CSS px** с указанными WCAG исключениями. Наша дополнительная цель для основных touch-кнопок — **44×44px**. Keyboard navigation, visible focus, semantic headings, readable validation, locale-aware text.

**Google Core Web Vitals**: `LCP <= 2.5s`, `INP <= 200ms`, `CLS <= 0.1` на **75-м перцентиле** реальных посещений, отдельно desktop/mobile. Это внешние общие пороги, **не измеренные характеристики CodeProgress**. При локальной разработке Lighthouse и Playwright дают лабораторные сигналы, а не полную замену полевых данных.

### Internal acceptance checks

- Нет горизонтальной прокрутки на 320/390/768/1440px.
- Базовые текстовые пары проходят автоматическую contrast-check.
- Без мыши доступны main nav, forms, dialogs, RU/EN.
- С `prefers-reduced-motion` нет необязательных анимаций.
- Ни один overlay не перекрывает mobile controls.
- Полный ru/en перевод, не переводятся пользовательские данные.
- Devtools console errors 0 в основных user journeys.
- LCP/INP/CLS оценить на production-like build; записать честные исходные и финальные значения при одинаковых условиях.

## 9. UX и продуктовые метрики

**Не выдавать целевые значения за бенчмарки рынка или измеренные результаты.** Сначала снять baseline на текущем UI; затем провести сравнение до/после.

| Метрика                       | Определение                                                                | Целевая гипотеза (не факт)                 | Как измерять                                      |
| ----------------------------- | -------------------------------------------------------------------------- | ------------------------------------------ | ------------------------------------------------- |
| First-action clarity          | Может ли пользователь без подсказки назвать следующий шаг после 10 секунд  | >=4 из 5 тестируемых                       | Небольшой ручной usability test                   |
| Task success rate             | Создать тему → задачу → занятие без помощи                                 | >=4 из 5                                   | Наблюдение за реальными пользователями            |
| Time to first task            | От входа до первой созданной задачи                                        | медиана <=2 мин                            | Тайминг с согласием на тест                       |
| Continue-task discoverability | Найти существующую активную задачу                                         | >=4 из 5 за <=20 сек                       | Модерируемый тест                                 |
| Learn-loop completion         | Доля активированных пользователей, сделавших тему+задачу+занятие за 7 дней | Baseline → проверка улучшения              | События, только после согласования privacy-policy |
| Weekly practice participation | Пользователи с >=1 подтверждённым занятием/7 дней                          | Baseline; без произвольного обещания роста | Агрегированная аналитика                          |
| Repeat-week engagement        | Возврат и запись реального занятия во вторую неделю                        | Baseline и когортное сравнение             | Агрегированная аналитика                          |
| Task completion clarity       | Понимают ли люди `2 из 5` и что это не «освоение Java на 40%»              | >=4 из 5 правильно объясняют               | Короткий UX interview                             |

**Не считать:** одни только клики, общее время на странице, число созданных задач или минуты как доказательство реального learning gain. Для проверки знаний в будущем нужен отдельный продуктовый механизм (проверочные задания / самооценка с честной маркировкой), а не фальшивая диаграмма mastery.

**Для персонального продукта с одним пользователем** бессмысленно создавать статистические выводы по D7 retention: сначала ручная проверка собственной полезности, затем — добровольные тесты с небольшой группой.

## 10. Приоритизация: не переделывать всё одним PR

### Phase A — Foundation & Dashboard (P0)

1. Audit repo, определить реальные frontend routes и DTO/вызовы API.
2. Дизайн-токены v2, `Button`, `Card`, `Badge`, `Progress`, `EmptyState`, `Skeleton`.
3. Topbar/sidebar/mobile nav без фиктивных ссылок.
4. Dashboard redesign: compact hero + real next task + real task count + study summary + real learning path или честный fallback.
5. Исправить некорректные формулировки («100% знаний») и email в hero.
6. ru/en, accessibility, existing functionality.
7. Manual approval in user's browser before changing other pages.

### Phase B — Topics & Tasks (P0/P1)

1. Новый Topics list: card title, description, status, real `done/total`.
2. Topic details: задачи с понятными статусами и next step; «учебный путь» только по реальным задачам.
3. Task details: цель, статус, priority, difficulty, deadline если поле реально есть; читаемые действия; одна primary CTA.
4. Не менять enum/API. Не добавлять fake route, если API не поддерживает глобальный список.

### Phase C — Study Sessions & Auth (P1)

1. Быстрое создание занятия, ясное контекстное назначение, заметка «Что получилось / что дальше» (если это существующая свободная заметка — текст подсказки, без изменения контрактов).
2. Экран журнала занятий с readable dates, настоящей временной шкалой.
3. Login/Registration в той же дизайн-системе.
4. Loading/empty/error flows в едином стиле.

### Phase D — Measured gamification (future P2)

Только отдельная постановка с согласованным Backend: weekly goals, milestones, optional streaks, XP/achievements; точные серверные правила, восстановление после пропусков, opt-out, никаких ложных цифр. Не вписывать это в текущий UI без модели данных.

## 11. Guardrails для Codex

- Сначала сохранить незакоммиченные изменения локализации №48 и предыдущего редизайна №49. Никаких `git clean`, `git reset`, веток с потерей данных.
- В ходе редизайна не изменять существующие Backend/Docker/PostgreSQL и реальные записи в БД.
- Использовать существующие query hooks и DTO. Если Dashboard summary недостаточно для next task, оценить уже существующие endpoints, число запросов и owner scoping. Не допридумывать клиентские API.
- Нельзя брать демонстрационные значения из HTML-прототипа. Все карточки production UI должны выводить настоящие значения API или корректные пустые состояния.
- Не использовать `localStorage` для JWT, credentials, sensitive user data. ru/en preference оставить.
- Не запускать destructive E2E и не создавать sample data в реальном аккаунте.
- Не менять v1.0.0 tag. Не делать commit/push/deploy без разрешения.
- При screenshot/manual review проверить пропорции на реальном viewport пользователя, а не только Playwright 1440×900.

## 12. Definition of Done для Phase A

- [ ] Пользователь за 5–10 секунд понимает, что делать дальше (проверка с пользователем, не только кодом).
- [ ] Все CTA работают и ведут на существующие корректные маршруты.
- [ ] Логика выбора next step явно детерминирована: IN_PROGRESS → PLANNED → все DONE → нет задач; если выбор неоднозначен, не притворяться персонализированным AI.
- [ ] Нет «Soon» для уже доступных функциональных сценариев.
- [ ] Нет вымышленного completion %, daily streak, XP или числа минут.
- [ ] Новая навигация, dashboard, UI states адаптивны на указанных ширинах.
- [ ] WCAG 2.2 AA проверки и keyboard flows без очевидных блокеров.
- [ ] RU/EN смена без reload, даты и пользовательские title/notes не искажены.
- [ ] Unit/Vitest, typecheck, lint, build, изолированные mocked Playwright smoke проходят.
- [ ] Реальный пользователь вручную открывает приложение, узнаёт свой Topic, Task, Session и данные.
- [ ] Отчёт Codex фиксирует что реализовано/что отложено и скриншоты на desktop/mobile.

## 13. Research notes and references (проверено по публичным источникам)

1. **Nielsen Norman Group — [10 Usability Heuristics](https://www.nngroup.com/articles/ten-usability-heuristics/)**. 2024 review: clarity of state, match with real-world language, recognition vs recall, minimalist UI, actionable error recovery.
2. **Nielsen Norman Group — [Designing Empty States](https://www.nngroup.com/articles/empty-state-interface-design/)**. Пустые экраны должны объяснять состояние и давать конкретную точку входа в задачу.
3. **Duolingo — [The Science Behind the Home Screen Redesign](https://blog.duolingo.com/new-duolingo-home-screen-design/)**. Learning path даёт последовательность и помогает возвращаться к материалу; не копировать конкретный UI.
4. **Duolingo — [Core Tabs Redesign](https://blog.duolingo.com/core-tabs-redesign/)**. 2026: единая иерархия, интервалы, consistency, editorial craft, QA across tabs.
5. **Duolingo — [Time Spent Learning Well](https://blog.duolingo.com/time-spent-learning-well/)**. Даже сам продукт различает обучающе полезное время и просто время; эта идея укрепляет отказ от «минуты = mastery».
6. **W3C — [WCAG 2.2](https://www.w3.org/TR/WCAG22/)**. Контраст 4.5:1/3:1, не-текстовый контраст и target size 24×24 minimum с исключениями.
7. **Google web.dev — [Core Web Vitals](https://web.dev/articles/vitals)**. LCP <=2.5 sec, INP <=200ms, CLS <=0.1 at p75 field data.
8. **Li, Ma & Shi (2023) — [Gamification in learning: meta-analysis](https://pmc.ncbi.nlm.nih.gov/articles/PMC10591086/)**. 41 studies / 49 samples / >5071 participants; positive mean effect, heterogeneous by context.
9. **Khaer (2026) — [Second-order gamification meta-analysis](https://journal.privietlab.org/index.php/JMER/article/view/2343)**. 55 meta-analyses; предупреждение о возможном завышении эффекта и методологических ограничениях.
10. **USWDS — [Design Principles](https://designsystem.digital.gov/design-principles/)**. User research, измеримые результаты, повторные проверки с реальными людьми.

### Evidence limitations

- Перечисленные источники **не доказывают**, что наш конкретный редизайн повысит retention или качество обучения. Для этого нужны UX-тесты и последующие измерения.
- Неопубликованные или не измеренные «рынковыми бенчмарками» цифры в таблице продуктовых целей — **наши внутренние гипотезы**, а не ссылки на научные данные.
- Прототип `CodeProgress_UX_Prototype.html` содержит **только DEMO DATA** и не подключается к Backend.
